# ADR-0018: The transfers module

- **Status**: Accepted
- **Date**: 2026-11-12
- **Deciders**: Paul

## Context

- A transfer is a `transfers` row plus two legs in `transactions` ([ADR-0010](0010-data-model-and-user-isolation.md)). The leg on the source account is negative and the leg on the destination is positive; both have the same date and description.
- Domain rules (`Transfer`):
  - the two accounts are different and have the same currency;
  - an archived account is refused only when newly chosen;
  - a change updates both legs.
- Transactions already list transfer legs as read-only items with `transferId`, behind the cursor paging and filters of [ADR-0017](0017-transactions-and-tags.md). Creates can be made safe to send again with a client id.
- The version of a resource is its row's `xmin` ([ADR-0013](0013-error-responses-and-concurrency.md)). Changing a transfer changes its legs, not the `transfers` row.
- Roadmap:
  - recurring transfers (monthly savings) created by the `Worker`;
  - the PWA moving money offline;
  - transfers between currencies after the MVP;
  - multi-user.

## Decision

1. **One `TransferResponse`**: `id`, `fromAccountId`, `toAccountId`, `date`, `amount` (positive), `description`, `outgoingTransactionId`, `incomingTransactionId`, `version`.
2. **No transfer list**: legs are listed by `GET /api/transactions?kind=transfer`, and `transferId` opens `GET /api/transfers/{id}`. The module has get, create, update and delete only.
3. **The version of the `transfers` row covers the legs**: every update also rewrites that row, so a client that read an older version gets `412`. `ETag` and `If-Match` work as for every other resource.
4. **Optional client-chosen id** (UUIDv7) on create, with the same semantics as transactions: sent again, the existing transfer is returned with `200`; an id used by another user gives `409` `resource.conflict`. Leg ids are always generated by the server.
5. **No tags on transfers** in the MVP.

Delete removes the transfer and both legs for good (`ON DELETE CASCADE`), with `If-Match`.

Details: [backend/api-endpoints.md](../../backend/api-endpoints.md#transfers).

## Consequences

**Positive**
- The form "from account → to account" maps one to one onto the response; the leg ids link the transaction list and the transfer.
- One paging and filtering mechanism for every movement; the list of an account still explains its whole balance.
- Two devices editing the same transfer cannot overwrite each other, with the same headers as every resource.
- Moving money from the phone offline is as safe as recording an expense. Recurring transfers of the `Worker` can retry with their own ids.
- Transfers between currencies can add `toAmount` (or a rate) to the response and request without breaking clients.

**Negative**
- No list with one row per transfer: a list filtered on an account shows one leg, and the full list shows both legs of each transfer.
- An update writes three rows (two legs and the transfer).
- A transfer cannot be tagged; tags can be added later as an optional field applied to both legs.

## Alternatives considered

**The two legs as `TransactionResponse`** — Rejected. No new type, but the client rebuilds source and destination from the signs.

**`GET /api/transfers` with its own paging and filters** — Rejected for now. One row per transfer, but it duplicates the cursor and filters of transactions; it can be added without breaking anything.

**Composite `ETag` from the versions of both legs** — Rejected. No extra write, but a special format that no other resource has.

**No idempotency for transfers** — Rejected. A dropped connection would move the money twice.

**Tags on both legs** — Rejected for now. Complete, but two copies to keep in sync, and tag usage counts would double.
